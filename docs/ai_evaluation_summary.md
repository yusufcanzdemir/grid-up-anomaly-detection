# AI evaluation summary

Engineering evidence for the Grid Up risk engine (`src/grid_up_anomaly_detection/ai/`). All numbers below
were reproduced from a clean checkout of `main` @ `05b5bc0` plus the fixes on branch `duygu-ai-finalize`,
seed 42, on 2026-09-19. **They are synthetic-scenario results, not field accuracy.**

## 1. Approach

* **Why not thresholds alone.** A loose lug at 40 % load can run cooler than a healthy lug at full load,
  so a fixed °C limit either fires on load peaks or fires late. The engine therefore judges temperature
  *relative to what this module should read at this current*.
* **Physics / rules first.** Per module, a commissioning fit of `T_lug − T_cabinet ≈ a·LPF_τ((I/Ir)²·R_cu(T)) + b`
  gives a load-normalised heating index, phase asymmetry, residual and trend (`baseline.py`, `features.py`).
  Hard rules (arc trip, arc detected without trip, arc-system error, sustained thermal-image overload,
  condensation, sensor fault, absolute temperature) set risk floors that work with no model at all.
* **Isolation Forest** (`ml.py`) scores novelty on physics-normalised features. It is one noisy-OR group
  with weight 0.45, so **ML alone can reach at most risk 45 = WATCH**: it can never page anyone or reach
  CRITICAL on its own.
* **Explainability.** Every payload carries ranked reason codes with source (`thermal_model`,
  `tvoc2_arc_guard`, `isolation_forest`, …), severity, an additive contribution share, a suspected
  condition, a recommended action and a data-quality block (`docs/inference_contract.md`).
* **Risk status ≠ alarm lifecycle.** The engine emits `NORMAL/WATCH/WARNING/CRITICAL`. Alarm workflow
  (`models.AlarmLifecycle`: `CRITICAL → ACKNOWLEDGED → RESOLVED / NOT_RESOLVED / FALSE_ALARM`) belongs
  to the notification layer. Its initial state is named `CRITICAL`, but that means "open, nobody has
  acknowledged it" and is used for WARNING alarms too.

## 2. Data reality

* The organizer workbook is **not** in this repository and was **not available** on the machine used for
  this run, so the supplied-data audit (`scripts/audit_data.py`) could not be re-run here. An earlier
  analysis concluded that the supplied current series behaves like independent random samples rather than
  a daily load profile, and that the temperature/humidity sheet is empty. That conclusion is **not
  re-verified** in this run. Note that the script's conclusion sentence is fixed text; read it against the
  computed lag-1 autocorrelation and hourly means it prints.
* No field-labelled fault data exists. Faults are generated by a deterministic physical simulator
  (`simulator.py`: RC thermal model with copper resistance, psychrometrics, Poisson PD, TVOC-2 arc events)
  with module-to-module parameter spread. The detector does not share the simulator's equations; it fits
  its own first-order model.
* The six fleet modules `normal_0…5` are also the Isolation Forest training set, so their rows below are
  in-sample. The scenario modules are not used for ML training (only their first 7 days fit the thermal
  baseline, always before onset).

* Fault scenarios detected: **8/8**. Diagnosis correct: **8/8**.
* Median lead time over the three scenarios with a failure time: **73.3 h** (threshold comparator 31.6 h).
* Benign runs within expected status: **10/10** (6 fleet modules, normal LV, normal MV, benign transients
  with EMI spikes/drop-out/cold-load pickup, hot ambient day). Worst benign: `benign_transient` WATCH, risk 37.
* False WARNING episodes before onset: **0.000 per module-day**.
* Differences from the earlier local run, which used 3 fleet modules (now 6):
  * `arc_detected_no_trip` is new, added with arc mode 1.
  * For the fault scenarios that existed before, detection, delay, lead time and diagnosis are identical.
  * Benign max-risk values moved by a few points (e.g. `normal_1` 3 → 11, `benign_transient` 38 → 37).
    This is consistent with the larger Isolation Forest training set. Every benign run is still within
    its expected status.

**End-to-end, real transport.** The same scenario rows were published over MQTT
(`replay.py --via mqtt` → Mosquitto → `mqtt_to_db.on_message` → `POST /ingest` → `RiskEngine.update()`,
5-min stride; normal_operation 15-min stride). In the streaming path:

* **loose_connection:** first WARNING 73.2 h before failure, diagnosed `LOOSE_CONNECTION`, with
  `CONNECTION_HEATING`, `PHASE_ASYMMETRY`, `LUG_RESIDUAL` and `HEATING_TREND` reasons.
* **normal_operation:** stayed NORMAL (max risk 16).
* **arc (both modes):** `ARC_TRIP` and `ARC_DETECTED_NO_TRIP` were both CRITICAL at the first sample.
  Arc mode 1 sets SCADA `arc_status` = 4.
* **sensor_failure:** WATCH, confidence 0.85, with `temp_l3_c` listed as faulty and missing.

## 4. 100-module scale test (`scripts/scale_test.py --modules 100`)

Apple M3 Pro (11 cores, 18 GiB), macOS, Python 3.12, single process, 26 h buffer at 1-min cadence
(1561 rows/module), full `RiskEngine.update()` path incl. Isolation Forest:

| inferences | throughput | mean | p50 | p95 | p99 | max | peak RSS | CPU for 100 modules @ 1 reading/min |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1000 | 13.1 /s | 76.4 ms | 75.5 ms | 79.8 ms | 96.5 ms | 130.3 ms | 290 MB (+26 MB buffers) | 0.127 core |

Latency grows with buffer length (every update re-scores the 26 h window). This is fine for 100 modules
at 1-min polling on one core. It is not an optimised streaming implementation.

## 5. Known limitations

* No field-labelled dataset. Every threshold is `[PLACEHOLDER]`/`[ASSUMPTION]` in `configs/default.yaml`
  and must be validated by a domain engineer. None is an authoritative electrical limit.
* `rules.abs_temp_critical_c` is now 125 °C, the same as the selected lug-probe minimum range, so there is
  no measurement headroom. In the scenarios it never fires (max lug temperature 96 °C). Detection relies on
  the load-normalised thermal model and the `ABS_TEMPERATURE` evidence ramp (70–95 °C).
* Arc mode 1 (`arc_detected_no_trip`) is **derived** (TVOC-2 regs 210/211 set while 212 == 0). No mode
  register is documented, and it must be verified on a real device.
* MPR-53CS: 32-bit word order and whether currents are already multiplied by the CT ratio are **unresolved**.
  The repository contains no field-side Modbus reader. Current reaches the engine only as canonical
  `current_*_a` values over MQTT/HTTP.
* PD is simulated only (MV_CELL). There is no acquisition chain. PD is gated by data presence (a baseline
  is fitted only when the channel reports), not by the `profile` field.
* Health and status need about 26 h of history per module. A cold module runs rules-only until its
  buffer and commissioning baseline exist.

## 6. Reproduce

```bash
poetry env use python3.12            # pandas<2.2 has no wheels for Python 3.13+/3.14
poetry install --all-extras
poetry run pytest -q && poetry run ruff check src/grid_up_anomaly_detection/ai
poetry run python src/grid_up_anomaly_detection/ai/scripts/generate_synthetic.py
poetry run python src/grid_up_anomaly_detection/ai/scripts/train.py
poetry run python src/grid_up_anomaly_detection/ai/scripts/evaluate.py
poetry run python src/grid_up_anomaly_detection/ai/scripts/scale_test.py --modules 100
GRIDUP_SUPPLIED_EXCEL=/path/outside/repo.xlsx poetry run python src/grid_up_anomaly_detection/ai/scripts/audit_data.py
# end to end over MQTT (broker + main.py/uvicorn + mqtt_to_db.py running):
poetry run python src/grid_up_anomaly_detection/ai/scripts/replay.py --scenario loose_connection --via mqtt
```
